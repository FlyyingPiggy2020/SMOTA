# SMOTA 移植与 OTA 测试用户手册

> **适用版本**：当前 SMOTA 单分区覆盖升级版本  
> **编写日期**：2026-04-29  
> **参考工程**：`examples/stm32g0_single_demo`  
> **目标读者**：需要把 SMOTA 移植到自己 MCU/产品工程的嵌入式开发者

---

## 1. 当前方案能做什么

当前 SMOTA 版本面向 **单分区覆盖升级**：

- Boot 固定烧录，后续不通过 OTA 更新 boot。
- App 被 OTA 直接覆盖写入，升级失败后不保证旧 app 可运行。
- Boot 通过 noinit RAM magic 和捕获窗口进入升级服务；如果 app 无效，下次复位继续停留在 boot 等待重新升级。
- 当前不做断点续传，也不再维护 `IN_PROGRESS/APP_VALID` Flash 状态；单分区升级中断电后是否能跳 app 只由向量表和 app info 判断。
- 当前不启用加密和签名，后续如果需要再扩展。

参考 STM32G0 demo 的默认布局如下：

| 区域 | 地址 | 大小 | 说明 |
|---|---:|---:|---|
| Boot 可执行区 | `0x08000000 ~ 0x080097FF` | `38KB` | boot 代码和只读数据 |
| 保留 Flash | `0x08009800 ~ 0x08009FFF` | `2KB` | 当前跳转逻辑不再使用 |
| App 区 | `0x0800A000 ~ 0x0803FFFF` | `216KB` | OTA 写入目标 |
| App info | `0x0800A200 ~ 0x0800A21F` | `32B` | 固件版本和项目 ID |
| Boot request RAM | `0x20000000 ~ 0x20000007` | `8B` | app 请求进入 boot 的 RAM magic |

## 2. 工程目录怎么理解

移植时建议先把目录按职责看清楚：

| 目录/文件 | 作用 |
|---|---|
| `smota/` | SMOTA 核心库和 HAL 接口，正常移植时尽量不改 core |
| `examples/stm32g0_single_demo/boot` | STM32G0 boot 参考工程 |
| `examples/stm32g0_single_demo/boot/port` | boot 侧平台适配层，移植重点 |
| `examples/stm32g0_single_demo/app` | STM32G0 app 参考工程 |
| `examples/stm32g0_single_demo/app/port/smota_user_config.h` | app 侧 SMOTA 配置和版本信息 |
| `scripts/pack_ota.py` | 根据 app 的 AXF/ELF 和 HEX/BIN 生成 `.ota` |
| `smota_host/` | Python 图形上位机，用于串口/TCP OTA 测试 |
| `smota-tools.py` | 当前仓库的一键构建和打包脚本 |

推荐移植方式是：复制 STM32G0 demo 的 `boot/port` 结构，再逐个替换为自己芯片的 Flash、通信、系统、身份和 boot 策略实现。

## 3. 移植 Boot

### 3.1 配置 Flash 布局

boot 侧的 `smota_user_config.h` 负责描述 SMOTA 分区、通信缓冲区、超时和 boot request 地址，至少包括：

```c
#define SMOTA_MODE                     2
#define SMOTA_FLASH_BASE_ADDR          0x08000000U
#define SMOTA_FLASH_SIZE               0x00040000U
#define SMOTA_BOOTLOADER_SIZE          0x0000A000U
#define SMOTA_APP_SIZE                 0x00036000U
#define SMOTA_FLASH_PAGE_SIZE          0x00000800U
#define SMOTA_BOOT_CAPTURE_WINDOW_MS   500U
#define SMOTA_BOOT_REQUEST_ADDR        0x20000000U
```

注意事项：

- `SMOTA_MODE` 当前使用 `2`，表示单分区覆盖升级。
- `SMOTA_BOOTLOADER_SIZE` 是 boot 总分区大小，STM32G0 demo 为 `40KB`。
- STM32G0 demo 的 boot scatter 当前仍把可执行区限制为 `0x00009800`，最后一页保留但不再作为 Boot 控制页使用。
- `SMOTA_BOOT_REQUEST_ADDR` 必须和 app 侧一致，并且链接脚本要把该 RAM 区域留出来。
- `SMOTA_BOOT_CAPTURE_WINDOW_MS` 建议配置为 `500U`，用于上电/复位后捕获上位机 `QUERY`。

### 3.2 修改链接脚本

Boot 工程需要满足：

```text
Boot IROM: 0x08000000 / 0x00009800
Boot request RAM: 0x20000000 / 0x00000008 / UNINIT
普通 RAM 从: 0x20000008 开始
```

App 工程需要满足：

```text
App IROM: 0x0800A000 / 0x00036000
App vector: 0x0800A000
App info: 0x0800A200 / 0x20 / FIXED
Boot request RAM: 0x20000000 / 0x00000008 / UNINIT
普通 RAM 从: 0x20000008 开始
```

Keil scatter 参考：

- `examples/stm32g0_single_demo/boot/MDK-ARM/stm32g0_single_slot_boot.sct`
- `examples/stm32g0_single_demo/app/MDK-ARM/stm32g0_single_slot_app.sct`

### 3.3 实现 Boot HAL Driver

boot 侧需要注册完整的 `struct smota_hal`：

```c
static struct smota_hal g_smota_hal = {
    .flash = &g_smota_flash_driver,
    .comm = &g_smota_comm_driver,
    .crypto = NULL,
    .system = &g_smota_system_driver,
    .identity = &g_smota_identity_driver,
    .boot = &g_smota_boot_driver,
};
```

各 driver 的职责如下：

| Driver | 必须实现 | 移植重点 |
|---|---|---|
| `flash` | `init/deinit/read/write/erase/lock/unlock` | 地址参数是 OTA 目标区逻辑 offset，`0` 表示 app 起始地址 |
| `comm` | `init/deinit/send/receive` | 可用 USB CDC、UART、CAN、BLE 等，只要收发 smOTA 帧即可 |
| `system` | `get_tick_ms/system_reset` | `get_tick_ms` 必须能支撑超时和捕获窗口 |
| `identity` | `get_default_info/get_running_info` | 空 boot 返回 `0.0.0 + SMOTA_BOOT`，有 app 时读取 app info |
| `boot` | `should_stay_in_boot/jump_to_app` | 控制入口条件和跳转 app |

STM32G0 demo 的参考文件：

- `smota_port_flash.c`
- `smota_port_comm.c`
- `smota_port_system.c`
- `smota_port_identity.c`
- `smota_port_boot.c`
- `smota_port.c`

### 3.4 Boot 主循环

移植后，boot 用户代码应该尽量简单：

```c
void main_app_init(void)
{
    if (smota_port_init() != 0) {
        return;
    }

    if (smota_init() != SMOTA_ERR_OK) {
        (void)smota_port_deinit();
        return;
    }
}

void main_app_poll(void)
{
    (void)smota_poll();
    HAL_Delay(1U);
}
```

捕获窗口和跳转 app 已经由 `smota_poll()` 内部通过 `boot driver` 执行，用户不需要在主循环里判断是否跳 app。

### 3.5 进入 Boot 的两种方法

当前 SMOTA 进入 boot 有两种方法：

- 用户主动进入：app 收到业务侧升级命令后，写入 RAM magic 并复位。boot 启动后检测到 RAM magic，就清除 magic 并停留在 boot。
- 复位捕获窗口进入：每次上电或复位后，boot 都会保留一段短暂捕获窗口。窗口内如果收到有效 smOTA 报文，就停留在 boot；如果没有收到报文且 app 有效，就跳转 app。

第一种适合正常在线升级，业务 app 只需要在合适时机调用请求进入 boot 的 API。第二种是防升死兜底机制，用来处理 app 已损坏、app 无法主动跳 boot、升级中断后复位等场景。

因此，上位机如果要在设备复位后强制进入 OTA，应在 boot 捕获窗口内持续发送携带目标固件版本和目标项目 ID 的 `QUERY` 报文；如果窗口内没有任何有效报文，boot 会尽快跳转到有效 app，避免重启卡顿。

## 4. 移植 App

app 侧不需要填写 Flash 分区、MTU、工作区、升级模式等参数。分区边界由 boot 和 app 链接脚本决定，SMOTA 的擦写策略只在 boot 侧执行。

app 侧最小配置只需要两类信息：

- App info：`SMOTA_APP_PROJECT_ID` 和 `SMOTA_APP_VERSION_xxx`。
- Boot request RAM：`SMOTA_BOOT_REQUEST_ADDR`，并且该地址要和链接脚本中的 `.smota_boot_request` 区域一致。

STM32G0 demo 的 app 配置示例：

```c
#define SMOTA_BOOT_REQUEST_ADDR        0x20000000U

#define SMOTA_APP_PROJECT_ID           "STM32G0SS_APP"
#define SMOTA_APP_VERSION_MAJOR        1U
#define SMOTA_APP_VERSION_MINOR        0U
#define SMOTA_APP_VERSION_PATCH        0U
```

### 4.1 定义 App 固件信息

app 必须在一个 `.c` 文件中放置：

```c
#include "smota_app_info.h"

SMOTA_APP_INFO_DEFINE();
```

同时在 app 的 `smota_user_config.h` 中配置：

```c
#define SMOTA_BOOT_REQUEST_ADDR        0x20000000U

#define SMOTA_APP_PROJECT_ID           "YOUR_PRODUCT_ID"
#define SMOTA_APP_VERSION_MAJOR        1U
#define SMOTA_APP_VERSION_MINOR        0U
#define SMOTA_APP_VERSION_PATCH        0U
```

`project_id` 会写入 `.ota` 包，也会用于 `QUERY` 阶段的设备端准入判断。正常升级时，OTA 包 ID 必须和设备当前 ID 一致；空 boot 场景下设备当前 ID 为 `SMOTA_BOOT`，但会允许任意非空目标 App ID 进行首次升级。上位机勾选“强制升级”时，会在 `QUERY.flags.bit0` 置位，设备端收到后直接允许升级。

### 4.2 App 请求进入 Boot

app 收到业务侧升级命令后，可以写 RAM magic 并复位。这是“用户主动进入 boot”的推荐方式：

```c
#include "smota_boot.h"

void smota_request_bootloader_and_reset(void)
{
    smota_boot_request_set();
    NVIC_SystemReset();
}
```

同时 app 链接脚本要保证 `.smota_boot_request` 放在 `SMOTA_BOOT_REQUEST_ADDR` 对应的 `UNINIT` RAM 区域，避免复位时被清零。

如果 app 已经损坏或无法执行这段逻辑，boot 仍然可以依靠复位捕获窗口进入 OTA。上位机需要在设备复位后的捕获窗口内发送有效 `QUERY` 报文，让 boot 留在 OTA 服务中。

## 5. 构建与生成 OTA

### 5.1 安装 Python 依赖

在仓库根目录执行：

```powershell
pip install click pyelftools pyserial
```

### 5.2 一键构建 demo

当前仓库的一键脚本是：

```powershell
python .\smota-tools.py build
```

成功后应看到：

```text
stm32g0_single_slot_boot.axf - 0 Error(s), 0 Warning(s)
stm32g0_single_slot_app.axf  - 0 Error(s), 0 Warning(s)
OTA 打包完成: build\stm32g0_single_slot_app.ota
```

如果你的分支仍使用旧脚本名，也可能是：

```powershell
python .\fbtools.py build
```

### 5.3 手动构建和打包

如果不用一键脚本，可以先用 Keil 分别编译：

```text
examples/stm32g0_single_demo/boot/MDK-ARM/stm32g0_single_slot_boot.uvprojx
examples/stm32g0_single_demo/app/MDK-ARM/stm32g0_single_slot_app.uvprojx
```

然后生成 OTA：

```powershell
python .\scripts\pack_ota.py `
  --elf .\examples\stm32g0_single_demo\app\MDK-ARM\stm32g0_single_slot_app\stm32g0_single_slot_app.axf `
  --firmware .\examples\stm32g0_single_demo\app\MDK-ARM\stm32g0_single_slot_app\stm32g0_single_slot_app.hex `
  --output .\build\stm32g0_single_slot_app.ota
```

打包脚本会从 app AXF/ELF 的 `.smota_app_version` 段读取版本号和 `project_id`，并写入 `.ota` 内的 `manifest.json`。

## 6. 烧录与 OTA 测试

### 6.1 第一次烧录

建议按这个顺序测试：

1. 只烧录 boot。
2. 复位设备，让设备停留在 boot。
3. 运行上位机，使用 `.ota` 给设备升级 app。
4. OTA 成功后设备复位，boot 等待捕获窗口后跳转 app。
5. 再次复位设备，确认无上位机通信时能自动进入 app。

### 6.2 启动上位机

在仓库根目录执行：

```powershell
python -m smota_host
```

串口测试时：

- 传输方式选择 `串口`。
- 串口号选择设备枚举出的 USB CDC 串口，例如 `COM4`。
- 波特率保留默认即可，USB CDC 场景下通常不真正影响 USB 传输速率。
- OTA 文件选择 `build\stm32g0_single_slot_app.ota`。
- 如需跳过设备端项目 ID 或版本准入判断，可以勾选“强制升级”。
- 如果通过上电/复位捕获窗口进入 boot，可以先点击“连接并升级”，再给设备上电或复位；上位机会在“连接/捕获(s)”时间内持续发送携带目标固件信息的 `QUERY`，让 boot 收到有效 smOTA 报文后停留在 OTA 服务中。

### 6.3 预期现象

只烧 boot 时，查询设备信息应显示：

```text
当前设备版本 = 0.0.0
当前设备ID = SMOTA_BOOT
```

加载 OTA 后，固件信息应显示：

```text
固件版本 = app 中 SMOTA_APP_VERSION_xxx 配置的版本
固件ID = app 中 SMOTA_APP_PROJECT_ID 配置的 ID
```

OTA 成功后：

- 上位机日志显示 `FINISH` 成功。
- 设备复位。
- boot 在捕获窗口内未收到 smOTA 帧时跳转 app。
- STM32G0 demo app 会通过 USB CDC 每秒发送 `hello world`。

## 7. MAP 检查清单

每次移植或调整分区后，都要检查 map：

```powershell
Select-String `
  -Path .\examples\stm32g0_single_demo\boot\MDK-ARM\stm32g0_single_slot_boot\stm32g0_single_slot_boot.map `
  -Pattern "Load Region LR_IROM1"

Select-String `
  -Path .\examples\stm32g0_single_demo\app\MDK-ARM\stm32g0_single_slot_app\stm32g0_single_slot_app.map `
  -Pattern "RESET|.smota_app_version|Load Region LR_IROM1|Execution Region ER_APP_INFO"
```

STM32G0 demo 的正确结果应满足：

- Boot `LR_IROM1` 起始为 `0x08000000`，`Max` 为 `0x00009800`，实际 `Size` 小于 `0x00009800`。
- App `RESET` 在 `0x0800A000`。
- App `g_smota_app_version_info` 或 `.smota_app_version` 在 `0x0800A200`。
- App `LR_IROM1` 起始为 `0x0800A000`，`Max` 为 `0x00036000`。

## 8. 常见问题

### 编译报 `SMOTA_BOOT_REQUEST_ADDR must be defined`

说明工程包含了 `smota_boot.h`，但没有在 `smota_user_config.h` 中定义 RAM magic 地址。请显式增加：

```c
#define SMOTA_BOOT_REQUEST_ADDR 0x20000000U
```

并在链接脚本中把该地址留出来，不能被普通栈、堆或 `.bss` 覆盖。

### 打包报缺少 `.smota_app_version`

通常是 app 没有调用 `SMOTA_APP_INFO_DEFINE()`，或者链接脚本没有保留 `.smota_app_version` 段。确认 app 中有且只有一个 `.c` 文件定义了 `SMOTA_APP_INFO_DEFINE()`。

### 上位机提示项目 ID 不匹配

检查三处是否一致：

- app `smota_user_config.h` 的 `SMOTA_APP_PROJECT_ID`
- `.ota` 上位机显示的固件 ID
- 设备查询返回的当前设备 ID

空 boot 返回 `SMOTA_BOOT` 是正常的；已有 app 时应返回 app info 中的产品 ID。

### Boot 不跳 App

按顺序检查：

- app 向量表是否在 `SMOTA_APP_ADDR`。
- app 初始 MSP 是否落在有效 SRAM 范围。
- reset handler 是否落在 app Flash 范围。
- `0x0800A200` app info 是否存在且 magic 正确。
- noinit RAM magic 是否一直被业务侧写入。
- 500ms 捕获窗口内是否收到了有效 smOTA 报文。
- `boot->jump_to_app()` 是否正确关闭外设、SysTick、中断并设置 MSP/VTOR。

### OTA 失败后复位仍留在 Boot

如果 app 向量表或 app info 已经无效，这是预期行为。当前简化方案不再依赖 `IN_PROGRESS` 状态页；如果半写 app 仍然满足向量表和 app info 检查，Boot 可能在 500ms 窗口后跳转，需由看门狗复位和上位机窗口捕获兜底。

## 9. 移植完成标准

移植完成后，至少满足以下标准：

- boot/app 能独立编译，且 boot map 未超过 boot 可执行区。
- `.ota` 能由 `scripts/pack_ota.py` 正确生成。
- 只烧 boot 时，上位机显示 `0.0.0 + SMOTA_BOOT`，并能 OTA 写入 app。
- OTA 成功后设备复位，boot 捕获窗口超时后进入 app。
- OTA 擦写开始后断电或复位，设备下次启动停留在 boot，可重新升级。
- 已有 app 且无上位机通信时，设备复位后不会长时间卡在 boot。
