# SMOTA Boot 可移植性评审

> **文档性质**：当前代码评审结论  
> **编写日期**：2026-04-29  
> **评审范围**：`smota_core`、`smota_hal`、`examples/stm32g0_single_demo/boot`  
> **重要说明**：本文档记录当前代码状态下的评审判断，不作为正式设计规格

---

## 1. 结论

SMOTA 核心框架的可移植性比重构前明显增强，`flash / comm / system / identity / boot` 的职责边界已经开始清晰。

如果目标是 **STM32/Cortex-M 内部 Flash 单分区 boot**，当前方案迁移成本较低，主要工作集中在 Flash 布局、通信驱动、设备身份和跳转实现。

当前 SMOTA v1 的目标是 **单分区覆盖升级**。因此 core 中保留 single-slot 擦除、写入、校验流程是当前版本边界，不作为本轮问题处理。后续如果要支持双槽位、外部 Flash、搬运安装、差分升级或压缩包升级，再引入 storage/install 抽象会更合适。

---

## 2. Boot Driver 的作用

`boot driver` 可以理解成 boot 的“门卫和记账本”。

它负责回答三个问题：

- 当前升级状态是什么，是否已经进入 `IN_PROGRESS`。
- 当前是否应该继续留在 boot，而不是跳转 app。
- 如果可以进入 app，具体平台该如何完成跳转前清理和跳转动作。

`IN_PROGRESS` 和 `APP_VALID` 当前不表示断点续传，也不表示可以从掉电位置继续恢复。它们只服务于 single-slot 的安全启动策略：

- `IN_PROGRESS` 表示已经开始覆盖 app，但还没有确认升级完整成功。此时复位后必须留在 boot，等待重新升级。
- `APP_VALID` 表示上一次 OTA 完整成功。它本身不绕过 app 校验，boot 仍会检查 app 向量表和 app info。

因此，如果升级过程中掉电，目前不会自动续传，用户需要重新发起一次完整 OTA。这个设计的目标是“不升死”，不是“断点恢复”。

---

## 3. 滞留在 Boot 的情况

当前设计约定以下情况必须停留在 boot：

- App 写入 RAM magic 后复位，boot 检测到请求并清除 magic。
- port 的强制入口条件成立，例如按键、GPIO、备份寄存器或其他板级 hook。
- boot 控制页最新状态为 `IN_PROGRESS`，说明升级已经开始但没有成功完成。
- App 向量表无效。
- 固定地址 `0x0800A200` 的 app info 无效。
- Boot 捕获窗口内收到有效 smOTA 帧，core 设置 stay-in-boot 标志并进入 OTA 服务。
- 捕获窗口到期后尝试跳转 app，但 `jump_to_app()` 返回失败。

只有在“不满足上述滞留条件”并且捕获窗口超时后，SMOTA core 才会通过 `boot driver` 调用平台跳转逻辑进入 app。

---

## 4. 可移植性评价

### 4.1 做得好的地方

- `flash / comm / system / identity / boot` 已经拆开，核心边界比重构前清晰。
- Flash driver 的地址语义已经明确为 OTA storage 逻辑 offset，平台 port 可以自行映射到内部 Flash 或外部存储。
- `SMOTA_BOOT` 已经从 core 移到 port identity，核心层不再知道空 boot 的具体默认 ID。
- Boot 状态页采用 append-only 记录，适合 Flash 只能从 `1` 写到 `0` 的特性。
- 跳转 app 的平台动作收敛到 boot driver，用户主循环不需要自己复刻捕获窗口和跳转判断。

### 4.2 仍需注意的地方

- STM32G0 boot port 是清晰的参考实现，但不是可直接跨产品复用的通用 boot。
- App 起始地址、app info 固定地址、SRAM 范围、boot 控制页地址、Flash 页大小仍属于产品级配置。
- `SMOTA_BOOT_REQUEST_ADDR` 不应该有框架默认值，移植方必须在 `smota_user_config.h` 中显式填写。
- 当前 core 只面向 single-slot 覆盖升级；跨 MCU、外部 Flash、多分区升级需要下一阶段抽象 storage/install。

---

## 5. 后续建议

- 保持 single-slot 防升死能力为显式能力，避免移植方漏掉 boot driver 后仍然静默编译运行。
- 下一轮需要支持多分区时，再把容量判断、擦除、写入、校验读取、安装激活剥离成 storage/install 层。
- RAM magic 只是进入 boot 的一种 port 实现，后续可补充备份寄存器、GPIO、RTC backup register 等方式。
- 跳转前的平台清理动作应继续留在 port，例如 USB CDC、UART、CAN 或 BLE 的退出动作都不应该写进 core。

---

## 6. 总体判断

当前 SMOTA 已经具备通用 OTA 组件的雏形，但当前 boot 更准确地说是：

> 适用于 STM32G0 单分区覆盖升级的 boot 参考实现。

在单分区目标内，它的可移植性已经比较清晰；要扩展成跨存储介质、多分区、多安装策略的通用 boot，下一步重点应放在 storage/install 抽象，而不是继续堆叠当前 handler 内的 single-slot 逻辑。
