# smOTA 当前代码协议说明

> **文档性质**：按当前仓库代码反推  
> **文档版本**：v1.0  
> **编写日期**：2026-04-27  
> **适用范围**：当前 `smota_host` 主机实现、`smota_core` 协议处理实现、`examples/stm32g0` 端口实现  
> **重要说明**：本文档只描述当前代码已经实现的真实行为，不引用历史设计文档，也不代表未来目标协议

---

## 1. 概述

当前 smOTA 通讯协议是一套运行在 `TCP` 或 `串口` 之上的自定义二进制帧协议。

它分成两层：

1. **本地升级包格式**
   - 主机先读取 `.ota` 文件
   - `.ota` 是 ZIP 容器，只在主机本地使用
   - 设备并不会接收 ZIP，也不会解析 `manifest.json`
2. **链路通讯协议**
   - 主机把 `.ota` 中的固件提取出来
   - 然后通过 smOTA 帧协议与设备交互

本文重点描述第 2 层，也就是设备真正接收到的通讯协议。

---

## 2. 字节序与传输模型

- **字节序**：小端
- **承载方式**：
  - `TCP`：流式 socket
  - `Serial`：流式串口
- **协议边界**：靠帧头和 `length` 字段确定，不依赖底层包边界

---

## 3. 通用帧格式

当前通用帧结构定义在 `smota_core/inc/smota_packet.h`。

### 3.1 帧布局

```text
+--------+-----+------+-----+-----+--------+---------+-------+
| SOF    | Ver | Frag | Seq | Cmd | Length | Payload | CRC16 |
+--------+-----+------+-----+-----+--------+---------+-------+
| 5 Byte | 1   | 1    | 1   | 1   | 2      | N       | 2     |
+--------+-----+------+-----+-----+--------+---------+-------+
```

### 3.2 字段说明

| 字段 | 长度 | 当前代码行为 |
|:-----|:-----|:--------------|
| `SOF` | 5 | 固定为 ASCII `"smOTA"` |
| `Ver` | 1 | 当前主机固定发 `0x00` |
| `Frag` | 1 | 当前固定发 `0x00`，未实现分片 |
| `Seq` | 1 | 主机侧递增，设备响应侧当前固定写 `0` |
| `Cmd` | 1 | 命令字 |
| `Length` | 2 | Payload 长度，小端 |
| `Payload` | N | 命令相关数据 |
| `CRC16` | 2 | 对 `FrameHeader + Payload` 做 CRC16，小端存放 |

### 3.3 当前帧头结构

```c
struct smota_frame_header {
    uint8_t sof[5];
    uint8_t ver;
    uint8_t frag;
    uint8_t seq;
    uint8_t cmd;
    uint16_t length;
};
```

### 3.4 SOF

固定为：

```text
73 6D 4F 54 41
```

对应字符串：

```text
smOTA
```

## 4. CRC 规则

当前 CRC 实现位于 `smota_core/src/smota_packet.c`。

- 算法：`CRC-16-CCITT`
- 多项式：`0x1021`
- 初始值：`0xFFFF`
- 计算范围：从 `SOF` 开始，到 `Payload` 结束
- `CRC16` 自身不参与计算
- 发送时按小端附加在帧尾

## 5. 命令字定义

### 5.1 请求命令

| 命令码 | 名称 | 方向 | 说明 |
|:------|:-----|:-----|:-----|
| `0x01` | `HANDSHAKE` | 主机 → 设备 | 握手 |
| `0x02` | `HEADER_INFO` | 主机 → 设备 | 下发 hash / 签名等头信息 |
| `0x03` | `DATA_BLOCK` | 主机 → 设备 | 发送固件数据块 |
| `0x04` | `DATA_COMPLETE` | 主机 → 设备 | 通知数据传输完成 |
| `0x05` | `INSTALL` | 主机 → 设备 | 请求安装并重启 |
| `0x07` | `QUERY_VERSION` | 主机 → 设备 | 查询当前运行版本 |

### 5.2 响应命令

响应命令统一为：

```text
req_cmd | 0x80
```

所以：

| 请求 | 响应 |
|:-----|:-----|
| `0x01` | `0x81` |
| `0x02` | `0x82` |
| `0x03` | `0x83` |
| `0x04` | `0x84` |
| `0x05` | `0x85` |
| `0x07` | `0x87` |

## 6. 命令 Payload 定义

以下结构均按 `#pragma pack(push, 1)` 紧凑布局。

### 6.1 `0x01 HANDSHAKE`

#### 请求

```c
struct smota_handshake_req {
    uint8_t fw_version_major;
    uint8_t fw_version_minor;
    uint8_t fw_version_patch;
    uint32_t firmware_size;
    uint8_t project_id[16];
    uint16_t block_timeout;
    uint16_t check_timeout;
    uint16_t install_timeout;
    uint32_t total_timeout;
};
```

长度：`33 Byte`

#### 响应

```c
struct smota_handshake_resp {
    uint32_t error_code;
    uint32_t next_offset;
    uint16_t max_packet_size;
    uint16_t mtu_size;
    uint32_t flash_free_size;
    uint16_t block_timeout;
    uint16_t install_timeout;
    uint8_t capabilities;
};
```

长度：`21 Byte`

#### 当前设备真实行为

- 检查 `firmware_size <= SMOTA_FLASH_SIZE`
- 保存目标版本到 `ctx->firmware_version`
- 保存 `block_timeout` 到 `ctx->timeout_ms`
- `project_id` 当前会和设备固化的项目名称 ID 做严格比对
- `next_offset` 当前固定返回 `0`
- `max_packet_size` 当前固定返回 `256`
- `mtu_size` 当前固定返回 `512`
- `flash_free_size` 当前返回 `SMOTA_FLASH_SIZE`
- `block_timeout` / `install_timeout` 直接回显请求值
- `capabilities` 由编译宏决定

#### 当前字段实际意义

| 字段 | 当前实现状态 |
|:-----|:--------------|
| `fw_version_*` | 真实使用 |
| `firmware_size` | 真实使用 |
| `project_id` | 真实使用，必须和设备固化项目名称 ID 一致 |
| `block_timeout` | 真实使用，转存到 `ctx->timeout_ms` |
| `check_timeout` | 当前设备侧未使用 |
| `install_timeout` | 响应回显，主机侧用于重连等待 |
| `total_timeout` | 当前设备侧未使用 |

---

### 6.2 `0x02 HEADER_INFO`

#### 请求

```c
struct smota_header_info_req {
    uint8_t sha256_hash[32];
    uint8_t signature_r[32];
    uint8_t signature_s[32];
};
```

长度：`96 Byte`

#### 响应

```c
struct smota_header_info_resp {
    uint32_t error_code;
};
```

长度：`4 Byte`

#### 当前设备真实行为

- 只有在 `HANDSHAKE` 状态才允许进入
- 会擦除下载区
- 只有在编译时开启来源可靠性或传输可靠性时，才真正保存 `sha256/signature`
- 对当前 STM32G0 示例配置，这几个可靠性开关默认都是关闭的，所以它主要起“进入下一状态并擦除 Flash”的作用

---

### 6.3 `0x03 DATA_BLOCK`

#### 请求

```c
struct smota_data_block_req {
    uint32_t offset;
    uint16_t length;
    uint8_t data[];
};
```

固定头长度：`6 Byte`  
后接 `length` 字节数据

#### 响应

```c
struct smota_data_block_resp {
    uint32_t error_code;
    uint32_t received_offset;
};
```

长度：`8 Byte`

#### 当前设备真实行为

- 只允许在 `HEADER_INFO` 或 `TRANSFER` 状态下进入
- 只支持**顺序写入**
- `req->offset` 必须严格等于 `ctx->received_size`
- 写成功后 `received_offset` 返回新的累计写入偏移

#### 当前主机发送策略

- 主机实际每包数据长度：

```text
min(用户配置分块大小, 握手响应 max_packet_size - DATA_BLOCK 请求头长度)
```

- 当前设备握手返回 `max_packet_size = 256`
- `DATA_BLOCK` 请求头长度为 `6`
- 所以当前主机默认每块最大固件数据长度为 `250 Byte`

---

### 6.4 `0x04 DATA_COMPLETE`

#### 请求

```c
struct smota_transfer_complete_req {
    uint32_t total_size;
};
```

长度：`4 Byte`

#### 响应

```c
struct smota_transfer_complete_resp {
    uint32_t error_code;
};
```

长度：`4 Byte`

#### 当前设备真实行为

- 只允许在 `TRANSFER` 状态下进入
- 校验 `req->total_size == ctx->firmware_size`
- 校验 `ctx->received_size == ctx->firmware_size`
- 如果开启了来源可靠性或传输可靠性，还会重新读取下载区并计算 SHA-256，与 `HEADER_INFO` 中下发的 hash 比较
- 当前 STM32G0 配置默认不开启这两个可靠性选项，因此默认只做大小一致性校验

---

### 6.5 `0x05 INSTALL`

#### 请求

```c
struct smota_install_req {
    uint8_t force_install;
    uint8_t reserved[15];
};
```

长度：`16 Byte`

#### 响应

```c
struct smota_install_resp {
    uint32_t error_code;
    uint16_t estimated_time_s;
};
```

长度：`6 Byte`

#### 当前设备真实行为

- 只允许在 `COMPLETE` 状态下进入
- 当前设备侧**并没有真正使用** `force_install`
- 当前固定返回 `estimated_time_s = 5`
- 设置 `ctx->reset_pending = 1`

#### 安装后的设备行为

- 设备先回复 `0x85`
- 然后如果 `reset_pending = 1`
- 就立即执行 `system_reset()`

在 STM32G0 端口中，`system_reset()` 会在重启前：

1. 刷新下载区写缓存
2. 把 `ctx->firmware_version` 写入持久化版本页
3. 用 `ctx->firmware_version` 更新 `ctx->current_version`
4. 执行系统复位

---

### 6.6 `0x07 QUERY_VERSION`

#### 请求

```c
struct smota_query_version_req {
    uint32_t reserved;
};
```

长度：`4 Byte`

#### 响应

```c
struct smota_query_version_resp {
    uint32_t error_code;
    uint8_t fw_version_major;
    uint8_t fw_version_minor;
    uint8_t fw_version_patch;
};
```

长度：`7 Byte`

#### 当前设备真实行为

- `reserved` 当前被忽略
- 直接返回当前运行版本 `ctx->current_version`

## 7. 当前实际升级流程

### 7.1 主机流程

当前主机升级流程为：

1. 主机先本地解析 `.ota`
2. 建立连接
3. 发送 `0x07 QUERY_VERSION`
4. 主机本地比较“当前运行版本”和“目标版本”
5. 如需升级，发送 `0x01 HANDSHAKE`
6. 发送 `0x02 HEADER_INFO`
7. 循环发送 `0x03 DATA_BLOCK`
8. 发送 `0x04 DATA_COMPLETE`
9. 发送 `0x05 INSTALL`
10. 如启用了激活校验，等待设备重连后再次发送 `0x07 QUERY_VERSION`

### 7.2 当前设备状态流转

典型状态流转如下：

```text
IDLE
  -> HANDSHAKE
  -> HEADER_INFO
  -> TRANSFER
  -> COMPLETE
  -> INSTALL
  -> 系统复位
```

#### 各命令允许进入的状态

| 命令 | 当前状态要求 |
|:-----|:--------------|
| `0x01 HANDSHAKE` | 当前代码未显式限制 |
| `0x02 HEADER_INFO` | `HANDSHAKE` |
| `0x03 DATA_BLOCK` | `HEADER_INFO` 或 `TRANSFER` |
| `0x04 DATA_COMPLETE` | `TRANSFER` |
| `0x05 INSTALL` | `COMPLETE` |
| `0x07 QUERY_VERSION` | 无显式状态限制 |

## 8. 错误码说明

### 8.1 线上的 `error_code`

大多数响应包中的第一个字段都是：

```c
uint32_t error_code;
```

`smota_packet.h` 中定义了一组位图风格错误码：

| 名称 | 值 |
|:-----|:---|
| `SMOTA_ERR_PROTOCOL_MISMATCH` | `1 << 0` |
| `SMOTA_ERR_PROJECT_ID_MISMATCH` | `1 << 1` |
| `SMOTA_ERR_VERSION_MISMATCH` | `1 << 2` |
| `SMOTA_ERR_FLASH_INSUFFICIENT` | `1 << 3` |
| `SMOTA_ERR_DATA_AES` | `1 << 8` |
| `SMOTA_ERR_FLASH_WRITE` | `1 << 9` |
| `SMOTA_ERR_VERIFY_SHA256_FAILED` | `1 << 17` |
| `SMOTA_ERR_VERIFY_SIGN_FAILED` | `1 << 18` |
| `SMOTA_ERR_INSTALL_FLASH_READ` | `1 << 19` |
| `SMOTA_ERR_INSTALL_LOW_BATTERY` | `1 << 20` |
| `SMOTA_ERR_INSTALL_BUSY` | `1 << 21` |
| `SMOTA_ERR_INSTALL_VERSION_OLD` | `1 << 22` |

### 8.2 当前代码中的实际问题

当前实现里，`error_code` 语义**并不完全统一**：

- 有些路径写入的是上面的位图错误码
- 但也有些路径直接写入内部枚举 `smota_err_t`

例如：

- `SMOTA_ERR_INVALID_STATE` 是内部枚举值 `1`
- 当它被直接写入 `error_code` 时，链路上看到的值也是 `1`
- 但 `1` 同时又会和位图定义里的 `SMOTA_ERR_PROTOCOL_MISMATCH` 冲突

所以当前代码下：

- `error_code == 0` 表示成功，这个是可靠的
- `error_code != 0` 只能表示失败
- 但**非零值的具体语义并不完全规范**

这属于当前实现上的真实现状。

## 9. 当前能力位

握手响应中的 `capabilities` 来自编译开关：

| 位 | 名称 | 含义 |
|:---|:-----|:-----|
| bit0 | `SMOTA_CAP_SIGNATURE` | 支持签名验证 |
| bit1 | `SMOTA_CAP_ENCRYPT` | 支持加密传输 |
| bit2 | `SMOTA_CAP_ANTI_ROLLBACK` | 支持防回滚 |

### 当前 STM32G0 示例配置

当前 `examples/stm32g0/port/smota_user_config.h` 中：

- `SMOTA_RELIABILITY_SOURCE = 0`
- `SMOTA_RELIABILITY_TRANSMISSION = 0`
- `SMOTA_RELIABILITY_VERSION = 0`

所以当前 STM32G0 示例设备上：

- `capabilities = 0`
- 不做签名验证
- 不做加密
- 不做设备侧防回滚

## 10. 当前实现限制与真实特性

### 10.1 已实现

- 固定 SOF 帧同步
- CRC16 校验
- 基于 `length` 的变长 payload
- 基于命令字的请求/响应
- 顺序数据块写入
- 传输完成一致性检查
- 安装后复位
- 运行版本查询
- 串口和 TCP 两种承载

### 10.2 当前未真正实现或只实现了一半

- 断点续传
- 分片发送
- 响应序号管理
- 设备侧真正使用 `force_install`
- 设备侧使用 `check_timeout`
- 设备侧使用 `total_timeout`
- 统一规范的线上错误码语义

### 10.3 当前重要事实

- `next_offset` 当前固定为 `0`
- `force_install` 当前主要只是主机侧逻辑
- 当前设备真正的超时控制只有 `block_timeout -> ctx->timeout_ms`
- 主机会校验 `.ota` 内部固件 SHA-256，但设备默认并不一定会再次校验

## 11. 接收与同步恢复机制

设备侧接收逻辑位于 `smota_core/src/smota_core.c`。

### 11.1 接收方式

- 使用固定 `1024 Byte` 接收缓冲区
- 非阻塞接收
- 每次轮询都尝试从缓冲区中提取完整帧

### 11.2 异常恢复

当前支持以下恢复方式：

- 如果数据不以 `smOTA` 开头，尝试在缓冲区中搜索下一个 `SOF`
- 如果 `length` 明显异常，尝试丢弃坏数据并重同步
- 如果未找到任何 `SOF`，清空缓冲区

### 11.3 超时

- 超时基于 `ctx->timeout_ms`
- 该值在握手阶段由 `block_timeout` 写入
- 超时后设备进入 `ERROR` 状态
- 当前不会主动向主机发送超时错误响应

## 12. 主机本地 `.ota` 文件格式

这不是链路协议的一部分，但它是当前主机升级流程的前置条件。

### 12.1 `.ota` 本质

`.ota` 当前本质上是一个 ZIP 容器。

### 12.2 必要文件

- `manifest.json`
- 一个固件文件
  - `.bin`
  - 或 `.hex`

### 12.3 当前 `manifest.json` 至少包含

- `format_version`
- `firmware_name`
- `firmware_format`
- `firmware_size`
- `firmware_sha256`
- `project_id`
- `fw_version`

### 12.4 主机处理方式

1. 解压 `.ota`
2. 读取 `manifest.json`
3. 校验必要字段
4. 读取内部固件
5. 若是 `.hex`，先解析成连续二进制镜像
6. 校验内部固件 SHA-256
7. 再进入链路协议流程

设备并不会看到 `.ota` 或 `manifest.json`。


## 14. 结论

当前代码实现的 smOTA 协议，本质上是一套：

- 固定帧头
- 小端字段
- CRC16 校验
- 请求 / 响应命令字
- 顺序分块传输
- 安装后复位

的轻量级流式通讯协议。

如果后续要继续演进协议，当前最值得优先收敛的点是：

1. 统一线上 `error_code` 语义
2. 明确 `project_id` 的长度和编码规范
3. 明确 `force_install` 的设备侧行为
4. 明确 `next_offset` 的断点续传语义
5. 进一步明确 manifest 的扩展字段策略
