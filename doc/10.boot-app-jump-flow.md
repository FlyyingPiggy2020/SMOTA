# SMOTA Boot 与 App 跳转路径总结

> **文档性质**：当前代码行为总结  
> **编写日期**：2026-04-30  
> **分析范围**：`smota_core`、`examples/stm32g0_single_demo/boot`、`examples/stm32g0_single_demo/app`

---

## 1. 总览

当前 STM32G0 单分区 Demo 的 Boot 跳转逻辑已经收口为三件事：

- **noinit RAM magic**：App 主动请求进入 Boot。
- **500ms 捕获窗口**：断电重新上电后给上位机发送 `QUERY` 的机会。
- **App 有效性检查**：窗口结束后，只有向量表和 app info 都有效才跳转 App。

当前实现不再使用 Flash 中的 `IN_PROGRESS/APP_VALID` 持久状态。升级成功后 Boot 复位，重新进入 500ms 捕获窗口；窗口内无有效报文且 App 有效时跳转新 App。

---

## 2. 关键地址

### 2.1 Flash 布局

STM32G0 单分区 Demo 的关键地址：

```c
#define SMOTA_FLASH_BASE_ADDR          0x08000000U
#define SMOTA_BOOTLOADER_SIZE          0x0000A000U
#define SMOTA_APP_SIZE                 0x00036000U
```

因此：

- Boot 起始地址：`0x08000000`
- App 起始地址：`0x0800A000`
- App info 地址：`0x0800A200`
- App 结束地址：`0x08040000`

Boot scatter 当前仍把可执行区限制为 `0x08000000 ~ 0x080097FF`，最后 2KB Flash 保留但不再作为 Boot 控制页使用。

### 2.2 Boot Request RAM

Boot 和 App 都把 `.smota_boot_request` 放在同一个 noinit RAM 地址：

```c
#define SMOTA_BOOT_REQUEST_ADDR        0x20000000U
```

链接脚本中该区域为 `UNINIT`，大小 8 字节：

```text
ER_BOOT_REQ 0x20000000 UNINIT 0x00000008 {
  *(.smota_boot_request)
}
```

Boot request 数据由产品代码本地定义，SMOTA core 不再提供 `smota_boot.h` 或通用结构体。STM32G0 demo 的 app 和 boot port 当前约定为两个 `uint32_t`：

```c
static volatile uint32_t g_smota_boot_request_area[2];
```

该 noinit 区域有两类有效值：

- Boot request magic：`request[0] == 0x53424F54` 且 `request[1] == ~0x53424F54`，表示 app 主动请求进入 boot。
- Reset marker：`request[0] == 0x3F4089FC` 且 `request[1] == ~0x3F4089FC`，表示 boot 曾经跳入 app，后续普通复位直接回 app。

`0` 或其他无效值都按断电上电路径处理。Boot 检测到无效值后会清零，避免随机 RAM 内容影响后续判断。

## 3. Boot 跳转到 App

### 3.1 Boot 主循环入口

Boot 工程的 `main_app_init()` 初始化 SMOTA port 和 core，`main_app_poll()` 每 1ms 调用一次 `smota_poll()`。

`smota_poll()` 的跳转决策集中在 core 的 boot poll 逻辑中：

1. 调用 `boot->should_stay_in_boot()` 读取产品侧启动策略。
2. 返回 `1` 时锁定 stay-in-boot，用于主动进入 boot。
3. 返回 `2` 时跳过 500ms 捕获窗口，直接尝试进入 app。
4. 返回 `0` 时进入 500ms 捕获窗口。
5. 捕获窗口内收到有效 SMOTA 帧后锁定 stay-in-boot。
6. 如果未锁定且捕获窗口已结束，则调用 `boot->jump_to_app()`。

STM32G0 Demo 中：

```c
#define SMOTA_BOOT_CAPTURE_WINDOW_MS   500U
```

### 3.2 STM32G0 Demo 的三态策略

STM32G0 port 的 `boot_should_stay_in_boot()` 只处理 noinit RAM，不再检查 app 有效性：

- 检测到 boot request magic：清除 magic，返回 `1`，永久停留 Boot。
- 检测到 reset marker：返回 `2`，跳过 500ms 捕获窗口并直接尝试跳 app。
- 检测到 `0` 或无效值：清零 noinit 区域，返回 `0`，进入 500ms 捕获窗口。

App 有效性只在 `boot_jump_to_app()` 中检查。`smota_port_is_app_valid()` 必须同时满足：

- App 向量表有效。
- 固定地址 `0x0800A200` 的 app info 有效。

App 向量表有效的条件是：

- App 初始 MSP 位于 SRAM 范围内。
- App Reset_Handler 位于 App Flash 区间内，即 `0x0800A000` 到 `0x08040000`。

App info 有效的条件是：

- 固定地址 `0x0800A200` 处的 `struct smota_app_info` 存在。
- `app_info->magic == SMOTA_APP_INFO_MAGIC`。

### 3.3 实际跳转动作

STM32G0 port 的 `boot_jump_to_app()` 会先再次检查 App 是否有效，然后执行：

1. 从 `0x0800A000` 读取 App MSP。
2. 从 `0x0800A004` 读取 App Reset_Handler。
3. 写入 reset marker，表示后续 app 运行中的复位直接回 app。
4. 停止并反初始化 USB 设备。
5. 执行 `HAL_RCC_DeInit()`。
6. 关闭全局中断。
7. 关闭并清空 SysTick。
8. 清除 NVIC 使能和挂起中断。
9. 清除 PendSV 和 SysTick pending。
10. 设置 `SCB->VTOR = 0x0800A000`。
11. 设置 MSP 为 App MSP。
12. 设置 `CONTROL = 0`。
13. 重新打开中断。
14. 调用 App Reset_Handler。

正常情况下，调用 App Reset_Handler 后不会再返回 Boot。

## 4. App 跳转到 Boot

App 工程中定义了进入 Boot 的接口：

```c
#include "smota_user_config.h"
#include "stm32g0xx_hal.h"

#define APP_BOOT_REQUEST_MAGIC 0x53424F54UL

static void app_boot_request_set(void)
{
    volatile uint32_t *request = (volatile uint32_t *)SMOTA_BOOT_REQUEST_ADDR;

    request[0] = APP_BOOT_REQUEST_MAGIC;
    request[1] = ~APP_BOOT_REQUEST_MAGIC;
}

void smota_request_bootloader_and_reset(void)
{
    app_boot_request_set();
    NVIC_SystemReset();
}
```

`app_boot_request_set()` 会向 `SMOTA_BOOT_REQUEST_ADDR` 写入产品约定的 magic 和反码：

```c
request[0] = APP_BOOT_REQUEST_MAGIC;
request[1] = ~APP_BOOT_REQUEST_MAGIC;
```

复位后 Boot 启动，检测到 magic 后：

- 在 `boot_should_stay_in_boot()` 内清除请求。
- 锁定 stay-in-boot。
- 不再跳转 App，等待上位机执行 `QUERY -> START -> DATA -> FINISH`。

这是 App 在线升级的推荐入口。

---

## 5. OTA 完成后的复位与跳转

OTA 成功后不会直接从 Boot 跳到 App，而是走一次系统复位：

1. `START` 处理成功后擦除 App 区。
2. `DATA` 按顺序写入 App 区。
3. `FINISH` 检查总长度和可选 SHA-256。
4. 校验成功后回复 `FINISH_RESP`。
5. Core 调用系统驱动 `system_reset()`。
6. STM32G0 port 先 flush staged write，延时 20ms，再调用 `NVIC_SystemReset()`。
7. 复位后 Boot 重新启动，等待 500ms 捕获窗口。
8. 窗口内无有效报文且 App 有效时跳转新 App。

当前简化方案不再依赖 `IN_PROGRESS` 防止跳入半写 App。若升级中断电，Boot 是否跳 App 取决于向量表和 app info 是否仍能通过检查。

---

## 6. App 无法主动跳 Boot 时的入口

如果 App 已卡死，或业务代码没有机会调用 `smota_request_bootloader_and_reset()`，仍然可以依靠捕获窗口进入升级：

1. 对设备断电后重新上电。
2. 上位机在 500ms 捕获窗口内发送有效 SMOTA 帧，通常是 `QUERY`。
3. Boot 成功解析帧后锁定 stay-in-boot。
4. 上位机继续执行完整 OTA。

这条路径依赖时序，上位机需要在捕获窗口内完成首次有效报文发送。App 运行后的外部复位、看门狗复位或软件复位会保留 reset marker，STM32G0 demo 会直接尝试跳 app，不进入 500ms 捕获窗口。

---

## 7. 移植注意点

- Boot 和 App 的 `SMOTA_BOOT_REQUEST_ADDR` 必须一致。
- Boot 和 App 链接脚本都必须把 `.smota_boot_request` 放在同一段 `UNINIT` RAM，且普通 `.bss/.data` 不能覆盖该区域。
- App 链接地址必须和 Boot 的 `SMOTA_PORT_APP_BASE_ADDR` 一致。
- App 必须通过 `SMOTA_APP_INFO_DEFINE()` 在固定位置生成 app info，否则 Boot 会认为 App 无效。
- Boot 跳转前要清理当前 Boot 使用过的外设、中断、SysTick 和向量表；不同 MCU 需要按平台改写 `boot_jump_to_app()`。
- 当前简化方案删除了 Flash 升级状态页，产品侧应结合看门狗、主动 boot request 和断电上电捕获窗口处理 App 卡死或半写 App 风险。
